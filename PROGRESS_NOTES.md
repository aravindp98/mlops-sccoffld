
---

### Key Concepts Learned:

#### 1. src/ Layout — Yen?
- Training logic aur serving logic separate panninom
- `main.py` ippo only serving — model load panni predict pannudu
- `src/` = pipeline stages, each file one responsibility

#### 2. DVC Pipeline (dvc.yaml) — Yen?
```
prepare → train → evaluate
```
- Each stage has `deps` (inputs) and `outs` (outputs)
- DVC automatically knows which stage re-run pannanum
- Only changed stages run aagum — efficient!

#### 3. params.yaml — Yen?
- Hardcoded values code-la vekkamal, yaml-la define pannuvom
- `test_size: 0.2`, `random_state: 42` — change panna easy
- DVC params track pannudu — param change aana stage re-run aagum

#### 4. .gitignore Fix — Important Learning!
```
# Wrong — entire folder ignore aana .dvc pointer also ignored
data/raw/

# Correct — contents ignore, .dvc pointer files allow
data/raw/*
!data/raw/*.dvc
```
- `.dvc` file = small pointer file → Git-la commit pannanum
- Actual `housing.csv` = DVC remote-la store aagum → Git-la vekka koodadhu

## STEP 3 — MLflow Model Registry ✅ DONE

### Enna panninom?
- `src/train.py`-la `registered_model_name="house-price-model"` add panninom
- Every `dvc repro --force` run → MLflow Registry-la new version auto create aagudhu

### MLflow UI-la Confirmed:
```
Model Name  : house-price-model
Version 1   : manually registered (UI-la)
Version 2   : auto registered via code (dvc repro --force)
Both runs   : linear_regression, 3.7s, train.py
```

### Model Registry Lifecycle:
```
None → Staging → Production → Archived

v1 = first manual run
v2 = auto registered via registered_model_name in code
Next = promote best version to Production via code
```

### Key Concepts Learned:

#### Manual vs Code Registration — Yen Code better?
```
Manual → UI-la click pannanum, human error possible, CI/CD-la pannala
Code   → Every run auto register, version auto increment, CI/CD friendly
```

#### registered_model_name — Yen?
```python
mlflow.sklearn.log_model(
    model,
    artifact_path="model",
    registered_model_name="house-price-model",  # This line auto registers
)
```
- Same name kuduttha → new version create aagum (v1, v2, v3...)
- Different name kuduttha → new model create aagum

#### --force flag — Yen?
```bash
dvc repro --force
# Nothing changed-nu DVC skip pannadu
# Force re-run pannudu → new MLflow run + new model version
```

### GCS-la Confirmed Structure:
```
mlflow/
├── <experiment-id>/artifacts/
│   └── params.yaml
└── models/
    └── <model-id>/artifacts/
        ├── MLmodel          ← model passport (flavors, versions)
        ├── model.pkl        ← actual trained model
        ├── conda.yaml       ← conda environment
        ├── python_env.yaml  ← python + pip environment
        └── requirements.txt ← exact package versions
```

### Key Concepts Learned:

#### Yen 5 files vendum?
```
model.pkl alone → run panna mudiyum, but which Python? which sklearn?
All 5 together  → exact environment reproduce pannalam
                   6 months later same results guarantee
```

#### MLflow Remote Architecture — 3 Options:
```
Option 1 (namma pannidhu) → SQLite local + GCS artifacts
  Learning-ku ok, team share panna mudiyadu

Option 2 (proper)         → MLflow server + Cloud SQL + GCS
  Team share pannalam, CI/CD friendly

Option 3 (managed)        → Vertex AI Experiments / SageMaker
  No server maintain pannanum, fully managed
  Namma Step 7-la itha pannuvom!
```

#### Backend Store vs Artifact Store:
```
Backend Store  → runs, metrics, params metadata (SQLite/PostgreSQL)
Artifact Store → model files, plots, artifacts (GCS/S3)

gs:// directly as tracking URI → NOT supported (learned the hard way!)
gs:// only for artifact store → SUPPORTED
```
